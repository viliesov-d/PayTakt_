# Правила Firebase у PayTakt v0.8.6 — що змінилося і чому

## Підтверджені факти

- У користувача з власним робочим простором збереження `workspaces/{id}/paySettings/current` працювало, якщо умова запису перевіряла `ownWorkspace(workspaceId)` і `request.resource.data.version == 5`.
- Із багатокомпонентною серверною перевіркою `validPaySettings()` повертався `permission-denied` навіть після успішної клієнтської перевірки. Точний підвираз, що відхиляє документ, **невідомий**, оскільки для нього не отримано Firestore Rules Emulator trace.
- Немає підстав міняти авторизацію, робочі простори або робити `allow write: if true`.

## Як працює v0.8.6

Лише шлях `/workspaces/{workspaceId}/paySettings/current` тепер дозволяє `create` та `update` за умов:

1. Користувач авторизований.
2. Він є `ownerUid` вибраного робочого простору.
3. Документ має `version == 5`.

В інших колекціях безпекові правила не змінено. Публічний доступ не ввімкнений.

**Компроміс безпеки:** це правило більше не перевіряє всі 37 полів та вкладені правила на сервері. `preparePaySettingsWrite()` і `verifyPaySettingsFirestoreShape()` залишаються в клієнті, тому звичайний інтерфейс продовжує перевіряти їх. Але власник, який використовує змінений клієнт або прямі запити Firebase, теоретично може записати некоректний документ версії 5 **у власний простір**. Це важливо, якщо у майбутньому з'являться командні ролі, критичні платіжні процеси або серверна обробка зарплат.

Для суворої серверної валідації знову потрібно локально відтворити запис і знайти помилкову умову в `validPaySettings()` через Firebase Emulator Requests. Не повертайте всю стару перевірку наосліп, бо проблема може відновитися.

## Як оновити безпечно

1. Зробіть резервну копію опублікованих правил у Firebase Console → Firestore Database → Rules.
2. Замініть **весь файл правил** на `firestore.rules` з v0.8.6, або змініть лише `match /paySettings/{payId}` у вже опублікованих відповідних правилах. Перевірте базу `(default)` проєкту `paytakt`.
3. Натисніть **Publish**.
4. Відкрийте PayTakt, виберіть робочий простір, збережіть «Правила оплати», оновіть сторінку.
5. У Firestore Data перевірте, що `workspaces/{обраний_ID}/paySettings/current` містить `version: 5` і ваші налаштування.
6. Ніколи не публікуйте `.env`, токени та приватні ключі Firebase.

## Команди Windows PowerShell

```powershell
npm.cmd install
npm.cmd test
npm.cmd run build
npm.cmd run dev
```

Тести npm підтверджують арифметику, клієнтську валідацію та **статичну наявність обмеження власника у файлі правил**. Вони НЕ замінюють запуск Firestore Emulator і НЕ підтверджують, що саме ваш сервер опублікував цей файл.

## Що робити, якщо відмова залишиться

Звірте назву Firebase-проєкту, активну базу `(default)` та фактично опубліковану умову `allow create, update`. При виконаній умові власника та документа v5 вона має відповідати вже підтвердженому користувачем успішному діагностичному варіанту.
